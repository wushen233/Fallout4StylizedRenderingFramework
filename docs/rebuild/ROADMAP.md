# 实施路线与视觉验收

## 0. 旧项目结案
等 B4 上传后独立读取 exact HEAD 及基线，追踪 Face SDF Debug 与生产路径，检查 Shadow Authority、Material Dispatch、DFPrepass/DFLight/DFComposite、双层阴影与 Refined Bands、Owner/Shader 变体、SSS/IBL/环境光、色调设置。记录证实/排除/未决结论；不能提前断言技术债务是唯一根因。保留历史，停止扩大 Eye NPR 调查。

## 1. 干净上游
经用户确认创建新实现工作区/仓库或分支，从当时最新上游 main exact HEAD 获取源码及子模块；记录 upstream remote，保留持续同步能力。只移植规划文档，不合并旧生产提交。不重置旧 main，不 force push，不删除历史，不改可见性。先验证上游原版构建、Shader、运行、基准画面/性能；形成可回滚安装。当前上游 SHA 仅观察，正式开始时重查。

## 2. 最小角色垂直切片
研究上游渲染接口与资源传输，选择最小真实材质功能验证架构。角色/材质声明、资源绑定、GPU 数据、Style Profile 的最小契约与 Face SDF 正常画面一起推进，不先搭建庞大全功能框架。Shinano（用户自制且较完整的角色）作为参考；VRoidHuman 尚未完成，不作首轮样本。允许隔离 NIF/BGSM/纹理适配，不覆盖原始资产。使用 Outfit Studio MCP、已有 SDF 工具；证实专业工具实际可用后再使用。后续引入成熟第三方种族验证通用性。

## 3. 角色功能排序
Face SDF → Hair NPR → Skin/SSS → Cloth/Leather/Metal → 角色阴影/Outline → 角色风格整合 → Eye NPR/高级材质。顺序可按视觉收益和具体依赖调整；不要在小面积细节长期停滞。各阶段均在正常画面验收生产效果，双风格差异逐步建立，而非等最终全部功能完成才测试。角色阶段使用现有场景验证，色彩管线基础调查和中性曝光基准同步开展。

## 4. 场景与全局视觉
角色基本完成并获得用户视觉认可后才正式扩展场景。优先复用上游场景能力；逐步开发场景材质、太阳/天空/局部光、间接光、反射、地形/植被/水、大气和天气。完整 LUT/色调分级、曝光/tone mapping 和后处理随实际需求实施，最终统一 Endfield/Exilium 角色与场景表现。

## 5. 每项生产功能门禁
- 确认确切源码、构建/Shader/ABI 与实际部署 winning provider，一致的 DLL/Shader/缓存身份。
- 同一模型、资源、镜头、姿态、天气、时间、曝光和场景，正常画面 Off/On 可辨识；必要时量化目标 ROI 与实际光照贡献，非目标区域保持合理不变。
- 专用模型/纹理/参数缺失、非法或不支持时 Native fallback；关闭/零强度恢复基线。实时调整和 Style 切换验证录制数据生命周期。
- 调试图、CPU 匹配、编译通过只是辅助证据，不能替代正常着色验收。若 Debug 成功但生产无差异，追踪实际生产数据写入、读取、资格、最终非零贡献；不要只继续添加 Debug。
- Face：正面/左侧/右侧/背光，头部动画与相机环绕。Hair：多角度、高光移动、发片边缘。材质：室内/室外/逆光、皮肤/织物/金属。颜色：中性参考、曝光固定与动态、亮部压缩/暗部、肤色与场景协调。
- 原生世界、未声明角色、其他 Feature 和复杂路径回归，记录明确支持边界。
- 性能：同一测试场景测 GPU/CPU 帧时间、VRAM、变体；以基线比较而非单次 FPS 截图。
- 用户决定艺术质量验收；Codex 本地实现/验证；独立 GitHub 审查完整调用链；分支和部署可追溯。不得默认合并、部署或启动游戏。
- 工具版本按实际兼容性/明确锁定；复用有效证据，不为无技术依据的版本偏好重复矩阵。

## 6. 开放设计事项
最终项目名称、仓库结构、新声明命名/schema、GPU 物理传输、真实上游版本及支持矩阵、Style Profile 格式、双风格纹理/曲线规范、颜色空间/曝光位置、具体性能预算均待基线及视觉研究验证。未经验证的候选不当作正式 ABI。
