Status labels: **VERIFIED** means directly present in the cited source or exact local tool output; **INFERRED** is a consequence that still needs runtime proof; **PROPOSED** is a design choice; **UNKNOWN** lacks adequate evidence; **BLOCKED** means this phase cannot responsibly settle it.

## Engine object and shader evidence

- **VERIFIED — Shape and runtime object are different identity layers.** CommonLibF4 `include/RE/B/BSGeometry.h:21-48` defines `BSGeometry` as `NiAVObject`, with property pointers and optional skin instance. `include/RE/N/NiObjectNET.h:31-51` exposes name and extra-data lookup on loaded scene objects; this is runtime representation, not a persistent asset key.
- **VERIFIED — A render pass carries a particular runtime geometry, shader property, shader, and descriptor.** `include/RE/B/BSRenderPass.h:29-48` exposes these references and `passEnum`. One geometry/property can participate in multiple passes; pass identity must not be used as material identity.
- **VERIFIED — Shader material has native coarse feature/type identities.** `include/RE/B/BSShaderMaterial.h:17-69` defines features including Face, SkinTint, HairTint and Eye, and material types Base/Effect/Lighting/Water. These are engine classification inputs, not a complete author semantic contract (for example, they do not split eye subparts).
- **VERIFIED — The lighting property points to a material and holds shader flags and render-pass collections.** `include/RE/B/BSShaderProperty.h:44-110,154-171`. `BSLightingShaderProperty.h:10-35` adds pass lists and a base technique ID. Neither property pointer nor pass pointer is a persistent identifier.
- **VERIFIED — A lighting material contains loaded textures, a texture-set reference and scalar values.** `include/RE/B/BSLightingShaderMaterialBase.h:21-75`; its `loadTextureSetLock` and load methods show texture loading is a separate lifecycle. `BSShaderTextureSet.h:8-26` exposes ten texture names at runtime. Texture path alone is not sufficient identity.
- **VERIFIED — NIF scene objects can carry named extra data.** `NiObjectNET.h:33-51`, `NiExtraData.h:16-32`, and `NiStringExtraData.h:7-48` expose named extra data and string values. This proves an API and a plausible authoring carrier, not that a proposed key/value encoding is supported by every target NIF editor/exporter or preserved through all asset pipelines.
- **VERIFIED — Native alpha controls exist separately from semantic material roles.** `BSGeometry.h:42-48` exposes the alpha property; `NiAlphaProperty.h:16-117` exposes alpha test/blend flags and blend factors. Shader descriptor `kAlphaTest` is translated into an injected define by `src/Render/ShaderFamilyDescriptor.cpp:70-73`. These signals do not prove an arbitrary material’s full render queue or that transparent draws enter the opaque deferred prepass.

## Current Community Shaders integration

- **VERIFIED — SSS classifies a prepass from the pass descriptor and resolves a reference/actor for a race-dependent profile.** `features/SubsurfaceScattering/src/SkinProfile.cpp:49-68` checks `kSkinTint | kFace`, then calls `TESObjectREFR::FindReferenceFor3D` and `Actor::race`. This is source evidence that this supported path can recover an owner for some geometry. It is not a general production identity contract or proof for all Shape types, command-buffer replays, or lifetimes.
- **VERIFIED — Extended Materials reads a lighting material’s loaded smoothness/specular mask texture and inspects its format.** `features/ExtendedMaterials/src/ExtendedMaterials.cpp:38-67`. This is a feature eligibility test, not a material registry or durable resource identity.
- **VERIFIED — Vanilla PBR selects shader contributions and publishes settings through the shared b7 substrate.** `features/VanillaPBR/src/VanillaPBR.cpp:45-105,120-138`; `src/Render/SharedDataLayout.h:113-153` declares PBR controls. It is an extension of selected existing lighting paths, not a replacement for the whole renderer.
- **VERIFIED — Descriptor bits such as Eye, Hair, SkinTint, Face and AlphaTest drive shader-family defines.** `src/Render/ShaderFamilyDescriptor.cpp:62-119`. Technique/pass descriptors describe a compiled rendering variant; they are not an author’s unique per-Shape material ID.
- **VERIFIED — Existing prepass lane offset is looked up from the native pixel-shader constant table.** `src/Render/ShaderSubclassHooks.cpp:225-250,274-285`. Do not hard-code an offset or reinterpret the existing lane in this work.

## Materials and asset tools available in this workspace

- **VERIFIED — Outfit Studio MCP inspected the installed Shinano race archive read-only.** `browse_archives` found `Avatars_Race - Main.ba2`; `load_from_archive` loaded NIFs from that archive without exporting or saving them. Samples included `meshes/avatars/shinano/head.nif` (103,222 bytes), `eyes/eye.nif`, `eyes/eyewhite.nif`, `eyes/eyelash.nif`, `eyes/eyebrow.nif`, `eyes/highlight.nif`, `faceparts/eyeparts.nif`, `faceparts/faceparts.nif`, `faceparts/head_rear.nif`, `faceparts/head_rear_t.nif`, `faceparts/tears.nif`, `hair/shinano_hair.nif`, and mouth teeth/tongue NIFs. Evidence came from Outfit Studio MCP `browse_archives`, `load_from_archive`, `get_shape_properties`, and `list_bones`; no UI automation was used.
- **VERIFIED — The sampled NIFs expose separate Shapes and BGSM references, but no F4SRF declaration.** The main head Shape is `head`, a skinned `BSSubIndexTriShape` with 2,341 vertices and 4,368 triangles, using `BSLightingShaderProperty` and `Materials\\Avatars\\shinano\\head.bgsm` (`BSLighting:4`). `head_rear` is a separate 1,599-vertex/2,980-triangle Shape using `FaceParts\\head_rear.bgsm` (`BSLighting:5`, `skinTinted=true`). The inspected Shape and NIF-root Extra Data arrays were empty in these samples. This does not establish that the proposed extra-data carrier cannot round-trip through other authoring tools.
- **VERIFIED — Eye/hair/face samples show both explicit separation and coarse shader overlap.** Separate NIFs provide Shapes named `Eye`, `EyeWhite`, `EyeBrow`, `EyeLash`, `HighLight`, `EyeParts`, `FaceParts`, `Hair_base`, `head_rear`, `Teeth`, and `Tongue`. `Eye` uses `BSLighting:16` and an alpha-test property (`GREATER`, threshold 128); `EyeWhite` and `HighLight` use `BSLighting:2`; `EyeBrow`, `EyeLash`, and `Hair_base` use `BSLighting:6`. The latter three therefore cannot be separated by that shader-type value alone. The inspected `Eye` NIF contains one combined Shape, so Iris/Pupil/Cornea subroles were not demonstrated as separate Shapes. The sampled main `head` is not `skinTinted`, while `head_rear` is; neither fact by itself defines the author's intended NPR role.
- **VERIFIED — NIF skinning names do not establish a stable GPU palette index.** Outfit Studio reports `head` weighted to the single named bone `HEAD`; `head_rear` uses `HEAD`, `Head_skin`, multiple neck/chest skin bones, and collarbone skin bones. The API output reports weighted bone names/weights, not the runtime GPU palette order or index.
- **VERIFIED — The same archive contains role-specific BGSM path families and many variants.** `browse_archives` listed `materials/avatars/shinano/eyes/{eye,eyebrow,eyelash,eyewhite,highlight,...}.bgsm`, `faceparts/{faceparts,head_rear,head_rear_tan}.bgsm`, and multiple `hair/hair_*.bgsm` variants. The NIF property references those BGSM paths. `read_material` could not read the BGSM while it remained packed in the BA2, so the BGSM payload values and texture semantics were not independently parsed in this pass. A separate BGEM example was not inspected.
- **VERIFIED —** Workspace tool sources include the `py-creation-lib` NIF core (`tools/bacup/py_creation_lib/native/nif_core`) and a BGSM/BGEM-aware material editor/conversion stack (`tools/bacup/py_creation_lib/native/materials`, `tools/bacup/ui/materials/field_registry.py`). No sample asset was rewritten or converted. Existing workspace reference samples also include backpack NIFs and BGSM files under `references/entries/ImprovedAnimatedBackPack/...`.
- **UNKNOWN —** These samples do not establish how NIF extra data survives FaceGen generation, outfit/mesh conversion, BA2 packaging, material swaps, or every effective provider configuration. They also do not prove runtime descriptor/pass coverage or that the Shinano archive observed by Outfit Studio is the winning provider in every game session.
